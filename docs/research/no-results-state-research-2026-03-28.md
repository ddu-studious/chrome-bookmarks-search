## 一、结论摘要

这次看完代码后，一个结论很明确：

**项目并不是“没有无结果兜底”，而是“已经有几个零散的兜底动作，但还没有形成一个能帮助用户恢复意图的完整无结果态”。**

当前已经具备的基础能力有：

- 输入像 URL 时，允许直接打开
- 本地无结果时，允许跳转默认搜索引擎
- 非历史模式下，会补充“最近访问”建议
- AI 模式下，支持语义搜索、相关推荐、向量索引构建

真正缺的是三件事：

1. **告诉用户为什么没搜到**
2. **优先帮用户在本地范围内恢复意图**
3. **只有本地恢复失败时，才把用户送去外部搜索**

因此，我建议把“无结果态”从一行文案升级为一个小型的 **恢复面板（recovery panel）**。  
优先级上，最值得先做的不是外部搜索建议，而是：

- 模式切换建议
- 过滤器 / 搜索语法纠偏
- AI 语义兜底
- AI 未就绪时的索引 / 配置引导

## 三、当前无结果态已经做了什么

### 3.1 基础兜底已经存在

如果用户输入了查询词，但本地结果为 0，目前系统至少会做两件事：

- 若看起来像 URL，给一个“直接打开”入口
- 给一个“使用默认搜索引擎搜索”的入口

这部分在三套 UI 上已经基本对齐，说明项目已经明确把自己定位成 **统一搜索入口**，而不只是本地书签过滤器。

### 3.2 项目也已经有“本地补救”的雏形

除了外部搜索，项目还已经具备两类更接近“恢复用户意图”的能力：

- 非 history 模式下的最近访问建议
- AI 模式下的语义搜索 / 当前页相关推荐

这很关键，因为它意味着：

**你已经有足够的技术积木，把无结果态做成“恢复流程”，而不是只做一个“去 Google/百度搜”的出口。**

### 3.3 但现状仍然是“动作有了，策略还没形成”

当前无结果态最大的问题不是功能缺失，而是策略缺失：

- 不区分“真无结果”和“假无结果”
- 不告诉用户当前为什么搜不到
- 不会优先引导用户切换模式、放宽条件、尝试语义搜索
- AI 不可用时，不同入口的提示强度不一致

## 四、为什么会出现“无结果”

从代码行为看，当前“无结果”至少有 5 种完全不同的成因。

### 4.1 真无结果：数据源里确实没有

例如：

- bookmarks 里没有这个页面
- history 范围内没有相关记录
- downloads 里没有对应文件

这种场景下，外部搜索或 URL 直开是合理的最后出口。

### 4.2 假无结果：模式选错了

这是当前最可能发生、也最值得产品化补救的情况。

例如用户在：

- `bookmarks` 模式搜一个只在历史里出现过的页面
- `tabs` 模式搜一个已经关闭、但保存在书签中的页面
- `downloads` 模式搜一个其实是网页标题的词

当前系统并不会告诉用户：

> “这个词在书签里没有，但在历史里有 6 条、标签页里有 2 条。”

这就让用户误以为“整个扩展都搜不到”。

### 4.3 假无结果：查询条件过严

`SearchParser` 当前支持：

- 空格分隔多关键字 AND
- 引号精确匹配
- 排除词
- `site:`
- `type:`
- `in:title` / `in:url`
- `after:` / `before:`

而且实现是严格过滤，尤其是：

- 多关键字默认是 **AND**
- 排除词命中即淘汰
- `site:` / `type:` / 时间过滤是硬条件

也就是说，很多“无结果”并不是没有，而是：

- 关键词太多
- 引号太死
- 过滤条件叠得太重
- 书签状态筛选（如 dormant / never_used）把结果挡掉了

### 4.4 假无结果：AI 能力没准备好

项目里虽然已经有 AI 检索和向量索引，但这条链路存在前置条件：

- AI 开关开启
- 有 API Key 或用户是 Pro
- 向量索引已经构建

也就是说，用户在“想搜但搜不到”的关键时刻，可能并不是没有 AI 能力，而是：

- AI 可用但没有被自动调用
- AI 不可用，但界面没有给出足够明确的下一步动作

### 4.5 空状态混淆：没有输入、没有数据、没有匹配，被同一种文案处理

当前代码里常见的文案是：

- `没有找到匹配的结果`
- `没有找到匹配的本地结果`
- `没有找到相关结果`
- `无结果`

但对用户来说，这几种状态其实完全不同：

- 我还没开始搜
- 我搜错模式了
- 我搜得太严了
- 本地没有，但 AI / 历史 / 外部搜索可能有
- AI 暂时不可用

如果不拆开，用户会自然把所有情况都理解为“这个扩展没帮上忙”。

## 五、当没有搜到结果时，可以为用户做什么

我建议按下面四层来设计无结果态。

### 5.1 第一层：先解释“为什么没结果”

无结果态的第一责任不是给链接，而是给解释。

建议在无结果区展示一个轻量原因条，至少告诉用户当前上下文：

- 当前模式：书签 / 标签页 / 历史 / 下载 / AI
- 当前过滤器：如 `never_used`
- 当前高级语法：如 `site:github.com`、`"react compiler"`、`-beta`
- 当前匹配规则：多关键字 AND

理想效果是让用户一眼知道：

> 我不是“搜不到”，而是“我现在在 bookmarks + dormant + site:github.com 这个窄范围里搜不到”。

这部分实现成本很低，因为 `SearchParser.parse()` 已经能解析出大部分条件，书签筛选状态也已在 UI 状态中。

### 5.2 第二层：优先帮用户在本地恢复意图

这是我认为最重要的一层。

#### 方案 A：模式切换建议

当当前模式结果为 0 时，展示跨模式建议按钮，例如：

```text
在以下来源继续找：
[历史记录 6] [标签页 2] [书签 0] [下载 0]
```

点击后直接切换模式并保留当前 query。

这比直接跳到搜索引擎更符合产品定位，因为你的产品本来就是多源统一搜索。

#### 方案 B：一键放宽查询

根据解析结果，给出“放宽搜索”的快捷动作：

- 清空书签状态筛选
- 去掉 `site:` / `type:` / 时间过滤
- 把 `"精确匹配"` 改成普通关键词
- 从 `A B C` 改成先尝试 `A B`
- 从 `A B` 改成分别尝试 `A` / `B`

建议文案不是解释规则，而是给按钮，例如：

- `清空筛选后重试`
- `去掉 site:github.com`
- `搜索 “react”`
- `搜索 “compiler”`

这类动作的好处是：

- 用户不用理解语法，只要点一下
- 可以把“没结果”转成“继续探索”

#### 方案 C：把“最近访问”从补充结果升级为显式救援

现在最近访问建议已经会在非 history 模式下追加，但它更像“附送一组结果”，不是明确的无结果救援。

建议在本地 0 结果时，把它升级为明确分组：

```text
本地没有精确匹配
你最近访问过这些相关页面：
...
```

这样用户感知会从“还是没搜到”变成“虽然没命中书签，但系统在帮我回忆最近看过什么”。

### 5.3 第三层：用 AI 做“语义救援”

这是项目现有能力里最值得利用、但目前没有充分接上的部分。

#### 方案 A：在普通模式下，0 结果时提供“尝试 AI 语义搜索”

当前语义搜索只在 AI 模式触发，这导致一个问题：

- 用户在 bookmarks 模式搜不到
- 系统其实有语义能力
- 但用户需要自己意识到“应该切去 AI 模式再搜一次”

这一步太重了。

更合理的做法是：

```text
没有找到精确匹配
[尝试 AI 语义搜索 “react compiler”]
```

第一版甚至不需要在当前列表内混排 AI 结果，只需要：

1. 检测 0 结果
2. 若 AI 可用，则展示 CTA
3. 点击后切换到 AI 模式并复用当前 query

这是一个非常适合当前架构的低风险方案。

#### 方案 B：AI 不可用时，明确告诉用户下一步

如果：

- AI 未启用
- 没有 API Key / 非 Pro
- 向量索引未构建

那无结果态里不该只是静默失败，而应该给到明确下一步：

- `去设置里开启 AI`
- `配置 API Key`
- `构建向量索引`

这部分项目已经有消息能力：

- `GET_EMBEDDING_STATUS`
- `OPEN_OPTIONS`
- Pro / API Key 状态检查

所以缺的不是基础设施，而是把这些动作挂进无结果态。

### 5.4 第四层：最后再给外部退出路径

只有在前面几层都失败，或者用户明确想跳出本地范围时，再给：

- `打开 URL`
- `使用默认搜索引擎搜索`

这两项现在已经做得不错，可以保留。

但建议它们在信息层级上排在：

1. 本地恢复
2. AI 救援
3. 外部搜索

而不是一开始就把用户送出产品。

## 六、推荐的无结果态设计稿

下面是一个更符合当前项目定位的无结果态结构。

```text
没有在「书签」中找到结果

当前条件：
书签 / dormant / site:github.com / 多关键字 AND

你可以试试：
[切到历史记录（6）] [切到标签页（2）] [清空筛选]
[去掉 site:github.com] [尝试 AI 语义搜索]

最近访问
- React Compiler RFC
- React Labs Update

其他操作
- 打开 https://react.dev
- 使用 Google 搜索 “react compiler”
```

这个结构的核心不是“多放几个按钮”，而是按照用户心理顺序组织：

1. 先告诉我发生了什么
2. 再告诉我本地还能怎么找
3. 再告诉我 AI 能不能帮忙
4. 最后才是去外部搜索

## 七、优先级建议

### P0：低成本高收益，建议先做

**目标**：让无结果态从“死路提示”变成“恢复面板”

建议项：

- 统一三套 UI 的无结果信息结构
- 展示当前模式 / 过滤器 / 高级语法原因条
- 提供 `清空筛选`、`去掉 site/type/时间过滤`、`去掉引号` 等快捷操作
- 强化“最近访问”分组的可见性

原因：

- 基本不需要新增底层能力
- 可以直接复用 `SearchParser` 和当前 UI 状态
- 对“假无结果”改善非常直接

### P1：中成本高收益，建议作为第二阶段

**目标**：把 AI 从独立模式升级为无结果救援能力

建议项：

- 0 结果时提供“尝试 AI 语义搜索”
- AI 不可用时提供 `构建索引 / 配置 API Key / 打开设置`
- Search Window / Content Script 也补上与 Popup 一致的 AI 索引引导

原因：

- 项目已经有 `INTELLIGENT_SEARCH`、`GET_AI_RECOMMENDATIONS`、`GET_EMBEDDING_STATUS`
- 这是最能体现项目差异化的“第二跳”
- 能把“搜不到”变成“用语义兜住”

### P2：中高成本，可在验证效果后再做

**目标**：让无结果态更个性化、更聪明

建议项：

- 本地记录 zero-result query（仅本地，不上传）
- 统计最常见的无结果词，辅助后续产品迭代
- 个性化推荐常用站点 / 常开标签 / 常搜主题
- 研究是否要做外部搜索建议（autocomplete）

原因：

- 需要额外状态管理与实验验证
- 隐私和合规边界要提前明确

## 八、不建议当前优先做的方向

### 8.1 不建议优先做外部搜索自动建议

原因和你现有文档里的判断一致：

- 复杂度高
- 涉及外部请求和隐私说明
- 产品收益未必比“本地恢复 + AI 救援”更高

参考现有调研：

- [搜索引擎集成调研](./search-engine-integration-research-2026-03-02.md)
- [搜索引擎集成 PRD](../requirements/search-engine-integration-prd-2026-03-02.md)

### 8.2 不建议把“无结果”默认理解成“去网页搜索”

因为你的项目已经具备：

- 多模式统一搜索
- 最近访问建议
- AI 语义搜索
- AI 当前页相关推荐

如果一无结果就直接把用户送走，等于浪费了这套系统最有价值的部分。

## 九、建议的落地顺序

### 第 1 步：统一无结果组件

在 `popup.js`、`content-script.js`、`search-window.js` 中抽出统一的无结果渲染思路，至少做到：

- 原因条
- 本地恢复动作
- AI CTA
- 外部搜索 CTA

### 第 2 步：做“查询放宽”

基于 `SearchParser.parse()` 生成建议按钮：

- 去掉引号
- 去掉排除词
- 去掉 `site:` / `type:` / 时间条件
- 降低关键词数量

### 第 3 步：做“跨模式救援”

先做最小闭环：

- 当前模式 0 结果时
- 展示几个模式切换按钮
- 保留 query 重新搜索

第一版甚至不需要精确计数，只要能一键切过去就已经有价值。

### 第 4 步：接上 AI 语义救援

用现有 `INTELLIGENT_SEARCH` 和 `GET_EMBEDDING_STATUS` 做第二跳：

- AI 已就绪：给“尝试 AI 搜索”
- AI 未就绪：给“构建索引 / 去设置”

## 十、建议追踪的指标

如果后续要把这个方向做成一个真正的产品能力，建议至少埋这几个本地指标：

- `zero_result_rate`
  - 搜索请求里，结果数为 0 的比例
- `zero_result_recovery_rate`
  - 无结果后，用户通过切模式 / 清筛选 / AI CTA 最终找到并点击结果的比例
- `external_fallback_rate`
  - 无结果后直接走搜索引擎跳转的比例
- `ai_rescue_ctr`
  - “尝试 AI 语义搜索”按钮点击率
- `index_block_rate`
  - 因为未构建索引 / 未配置 AI 而无法进入 AI 救援的比例

如果这些指标跑出来，后续你就能非常清晰地判断：

- 用户到底是“真的没内容可找”
- 还是“本来能救回来，只是现在界面没帮到他”

## 十一、最终建议

如果只保留一句话作为结论，我的建议是：

> **无结果态不应该只是“没搜到”，而应该是“帮用户恢复意图”的第二搜索入口。**

对这个项目来说，最值得做的方向不是继续堆更多搜索源，而是把现有能力串起来：

- 用模式切换解决“搜错范围”
- 用查询放宽解决“搜得太严”
- 用 AI 语义搜索解决“关键词没命中”
- 用外部搜索兜住“本地和 AI 都没有”

这样无结果态才会真正符合这个项目的定位：

**一个统一搜索入口，而不是一个结果为 0 就结束的过滤器。**
